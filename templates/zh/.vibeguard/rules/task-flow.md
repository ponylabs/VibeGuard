# 任务流程（Task Flow）

本工作流用于治理当前项目中的 AI 辅助变更。

VibeGuard 的目标是在保留 vibe coding 速度的同时，避免代码漂移、依赖膨胀、上下文遗忘和未验证变更。

变更边界遵守 `.vibeguard/rules/change-area.md`。

依赖、框架、构建工具、测试工具和包管理器变更遵守 `.vibeguard/rules/dependency-check.md`。

测试用例、静态检查、类型检查、构建检查和验证命令遵守 `.vibeguard/rules/test-plan.md`。

完成声明、验证证据、验证失败和验证缺口遵守 `.vibeguard/rules/final-check.md`。

state 读取、写入、证据标签和体积控制遵守 `.vibeguard/rules/state-update.md`。

项目事实、决策、风险和验证记录先读 `.vibeguard/state/state-index.md`，再只读取和当前任务相关的状态文件。

核心原则：

```text
默认保持快速。按风险升级治理。保持输出简洁。只用证据写入状态。
```

## 1. 任务模式

选择能安全完成任务的最轻模式。

不确定时选择更高风险模式，但输出仍保持简洁。

判定整个逻辑任务，而不是只判定下一次小编辑。

### 快速路径（Fast Path）

适用于极小、低风险变更：

- 拼写修正
- 注释调整
- 已触碰行的格式调整
- 少量文案修改
- 单行样式调整
- 不影响行为、依赖、API、数据或测试的变更

Fast Path 规则：

- 阅读 VibeGuard 入口
- 遵守 `.vibeguard/rules/change-area.md`
- 只检查直接相关的文件或区域
- 做最小必要修改
- 有必要时运行最小检查
- 不更新 `.vibeguard/state/`
- 最终回复控制在 1-3 行

Fast Path 不得新增依赖、修改测试、改变公开行为或触碰无关文件。

Fast Path 是白名单机制。出现以下任一情况，必须升级到 Standard Path：

- 编辑函数、类、组件、hook、API handler 或导出符号
- 修改条件判断、循环、错误处理、异步逻辑、数据流或业务规则
- 触碰被多个模块使用的文件，且行为可能变化
- 修改测试、配置、依赖清单、构建脚本、生成文件或锁文件
- 修改超过一个非文档文件
- 改变用户可见行为
- 在同一对话中，第二次或更多次以 Fast Path 触碰同一功能、文件、模块、API 或行为
- 无法确定影响面

### 标准路径（Standard Path）

适用于常规开发任务：

- bugfix
- 小功能
- 局部重构
- 现有模块内的行为变化
- 针对明确缺口新增或调整测试

Standard Path 规则：

1. 阅读相关 VibeGuard 规则和状态。
2. 有必要时简短复述任务。
3. 检查项目状态并定位影响范围。
4. 给出简短计划，通常 3-5 条。
5. 新增测试前，优先复用或调整现有测试。
6. 按最小范围实现变更。
7. 运行相关检查。
8. 只有项目知识发生变化且有证据支撑时，才更新治理状态。
9. 交付时说明变更、验证和未解决风险。

### 治理路径（Governed Path）

适用于高风险或高扩散半径变更：

- 新依赖、框架、构建工具或测试运行器
- 数据库 schema 或持久化数据格式变化
- 认证、授权、安全、支付或数据删除行为
- 大范围重构
- 跨模块架构变化
- 影响外部使用者的公开 API 或配置格式变化
- 大规模文件删除、重命名或迁移

Governed Path 规则：

1. 阅读相关 VibeGuard 规则和状态。
2. 检查受影响代码、测试、依赖和 open items。
3. 提出选项或计划，并说明风险和回滚点。
4. 触发 hard gate 时，先停止并等待确认。
5. 编码前定义测试和验证策略。
6. 只实现已批准的范围。
7. 运行静态检查、测试、构建或等效验证。
8. 用有证据支撑的变更更新治理状态。
9. 交付时提供版本管理建议。

## 2. 门禁（Gates）

Gates 用于阻止不可逆或高扩散风险错误，不应把每个任务都变成审批仪式。

Hard Gate 的含义是：停止继续改文件，并提出一个简洁问题。用户回复前不要继续实现。如果工具无法安全暂停，保持工作区不再变化，并报告触发的 gate。

### 硬门禁（Hard Gates）

以下情况必须停止并等待人类确认：

- 新增运行时依赖
- 新增开发依赖
- 新增或替换框架
- 修改测试框架、构建系统或包管理器
- 修改数据库 schema 或持久化数据格式
- 修改认证、授权、安全、支付或数据删除行为
- 删除、重命名或移动大量文件
- 因无关原因编辑密钥、凭证、生成文件、vendor 代码或锁文件
- 需求与 VibeGuard 规则或状态冲突，但仍要继续

### 软门禁（Soft Gates）

以下情况不一定停止，但必须在计划或交付中指出风险：

- 公开 API 形状变化
- 跨模块行为变化
- 配置行为变化
- 测试策略变化
- 性能敏感代码
- 错误处理语义变化
- 用户可见流程变化

当 soft gate 变更难以回滚、影响外部用户或扩散范围不清楚时，升级为 hard gate。

## 3. 测试策略

测试和静态检查遵守 `.vibeguard/rules/test-plan.md`。

新增测试前，优先复用或调整现有测试。

验证命令优先使用 `.vibeguard/state/project-commands.md` 中登记的固定项目命令。

如果没有登记命令，应从项目脚本、README、CI 或用户指令中查找；发现持久命令后，按证据更新 `.vibeguard/state/project-commands.md`。

## 4. 事实来源

`.vibeguard/state/` 是提示账本，不是真理来源。

state 描述当前项目，不得包含通用 VibeGuard 规则。

按以下优先级信任信息：

1. 当前用户指令
2. 代码、依赖清单、配置文件、测试和 CI 文件
3. 项目文档
4. `.vibeguard/state/`

如果 state 和可观察的项目现实冲突，信任项目现实，并报告 state 可能已过期。

Standard Path 或 Governed Path 中，在依赖 state 前，应尽量用项目现实校验相关结论：

- 已批准依赖：检查依赖清单或锁文件
- 测试命令：检查 package scripts、Makefile、pyproject、justfile、task 配置、README 或 CI
- API 形状：检查代码和测试
- 已关闭问题或风险：检查实现、测试或用户确认

不要把 state 当成那些可低成本从项目中检查到的事实的权威来源。

## 5. 验证

验证遵守 `.vibeguard/rules/final-check.md`。

测试、静态检查、类型检查、构建检查和固定命令选择遵守 `.vibeguard/rules/test-plan.md`。

声称任务完成前，必须有新鲜验证证据，或明确报告验证缺口和风险。

## 6. 治理状态策略

state 更新遵守 `.vibeguard/rules/state-update.md`。

Fast Path 不更新 state。

Standard Path 只在持久项目知识发生变化时更新 state。

Governed Path 在交付前检查是否需要更新 state。

## 7. 状态读取预算

state 读取预算遵守 `.vibeguard/rules/state-update.md`。

默认先读 `.vibeguard/state/state-index.md`，再只读取和当前任务相关的状态文件。

## 8. 反切片规则（Anti-Salami Rule）

不要把一个逻辑上连贯的变更拆成多个 Fast Path 任务来规避 Standard Path 或 Governed Path。

如果一串小编辑共同服务于同一个行为、架构、依赖、API、数据、测试或配置变化，应按最终目标中风险最高的模式分类。

如果连续小改动触碰同一功能、文件、模块、API 或行为，继续前重新评估任务模式。

## 9. 输出预算

治理应指导行动，而不是膨胀对话。

默认输出规则：

- 除非用户要求，不要打印完整 checklist
- 不要叙述显而易见的文件读取过程
- Fast Path 最终回复保持 1-3 行
- Standard Path 计划保持 3-5 条
- 只在 Governed Path 的风险、gate、依赖、API 变化、数据变化和验证缺口上保留详细推理
- 只报告未完成的检查项或有意义的风险

优先使用紧凑交付，而不是流程日志。

除非用户要求细节，使用以下最终回复格式。

Fast Path:

```text
Changed: ...
Verified: ...
```

Standard Path:

```text
Changed: ...
Verified: ...
Open: ...
```

Governed Path:

```text
Changed: ...
Verified: ...
State: ...
Open: ...
Version: ...
```

除非用户询问，不要解释工作流。

不要包含已经通过的内部 checklist 项。

## 10. 停止条件

出现以下情况时，停止并询问用户：

- 触发 hard gate
- 需求不清楚，继续实现会变成猜测
- 请求范围超出原始任务
- 连续小改动看起来属于一个更大的逻辑变更
- 调查后根因仍不清楚
- 必要验证无法运行，且风险有意义
- 无关既有测试失败阻塞信心
- 实现会与 VibeGuard 规则或 state 冲突
- 安全完成需要修改依赖、框架、数据格式、安全行为或大范围架构

停止时报告：

- 发现了什么
- 为什么继续有风险
- 建议用户做出的下一步决定

## 11. 完成规则

最终回复前，确保：

- 所选任务模式匹配风险
- 已阅读相关治理文件
- 实际可行时，已用项目现实校验相关 state
- 已检查影响范围
- gated changes 已获批准或已避免
- 新增测试覆盖前，已优先复用或调整现有测试
- 项目有范围内命令时，验证从项目命令运行；否则报告验证缺口
- governance state 只在项目知识有证据支撑地变化时更新
- 未经请求，不执行版本管理操作

最终回复不要复述此 checklist。只报告：

- 改了什么
- 验证了什么
- 什么没有验证或仍未解决
